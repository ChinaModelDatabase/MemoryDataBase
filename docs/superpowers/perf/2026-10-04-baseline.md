# MemoryDataBase MVP — 性能基线报告 (2026-10-04)

手工验收基线：`scripts/perf-report.sh`，本机运行。**未达标** — 目标为明文 RESP 小 value GET/SET ≥ 50 万 OPS/s，实测约 17 万 OPS/s（pipeline=1）。本文件记录真实数字与差距，不作达标声明。

| 项 | 值 |

| 主机 | MacBookAir.local |
| CPU 数 | 10 (`sysctl -n hw.ncpu`) |
| rustc | 1.99.0 (b940084d7 2026-09-28) |

## 对照目标的评估

- **目标**：明文 RESP 小 value GET/SET ≥ 500,000 OPS/s（spec §9 开文档验收线）。
- **实测（pipeline=1）**：SET ≈ 169k OPS/s，GET ≈ 175k OPS/s。
- **结论：未达标。** 差距约 **2.9–3.0×**（达到目标的 ~34–35%）。
- 这是**开发机基线**（MacBookAir, macOS arm64, 10 CPU），不是生产硬件上的认证数字；即便如此，架构层开销是主要瓶颈，换更快机器无法填补 3× 缺口。

### 已知架构开销（为何上不去）

当前 MVP 请求路径每条命令依次经历：

1. **Actor channel hop**（`jx-engine/src/actor.rs`）：每条命令经 `crossbeam_channel` 发往 shard actor 线程，再经 `std::sync::mpsc` 回传 reply。这是两次 channel 往返 + 两次线程唤醒，按命令计费。
2. **Mutex 分片锁**：actor 线程拿到命令后仍调用 `Engine::execute`，内部走 `lock_shard(sid)`（`Mutex`）。`actor.rs` 注释明确写明：actor 只是叠加在 Engine 内部 Mutex 之上的**额外**串行化层，尚未做到 shard 独占。
3. **每命令 RESP 编解码**：客户端与服务端均按命令逐条 encode/decode（`format!` + 字节拼接/解析），无 writev/批量聚合。
4. 连接任务本身跑在 tokio 多线程 runtime 上，channel 往返引入额外调度延迟（每请求 p50 ≈ 360 µs，64 client × ~2.8k ops/s/client ≈ 175k 聚合吞吐，与实测吻合）。

### 接近 500k 需要什么（spec §9.2 调优路径）

按收益从高到低：

1. **真正 shard 所有权**：删除 Engine 内部 per-shard `Mutex`，让 shard actor 独占其数据，channel hop 只做一次（或改为无锁共享结构），消除双重串行化。
2. **writev / 批量 I/O**：连接层将一个 pipeline batch 内的请求合并为一次 `writev`/单次 write，回复侧合并 batch 编码；减少 syscall 与 `format!` 分配。
3. **批量命令派发**：shard runtime 支持一次投递多条命令（pipeline 感知），摊薄 channel hop 成本。
4. **RESP 编码器热路径优化**：预分配缓冲、避免每命令 `format!`，或零拷贝 bulk reply。
5. **压测侧**：当前 `jx-cli bench` 每 client 串行往返；客户端也可能成为瓶颈。达到服务器侧 500k 后需用多进程/多网卡客户端验证（如 memtier_benchmark）。
6. **硬件**：服务器侧确认在多核 Linux x86_64 信创环境复测；本报告数字仅为 dev-machine baseline。

在完成 1–3 之前，不建议再用调 shard 数 / pipeline 参数的方式宣称逼近 500k —— pipeline=32 的 258k–307k 是批量换吞吐，不是每命令 500k。

## 复现

```bash
bash scripts/perf-report.sh
# 可选覆盖: PERF_CLIENTS=64 PERF_REQUESTS=100000 PERF_VALUE_SIZE=64 PERF_PORT=6399
```

脚本构建 release 二进制、写临时配置、`trap` 保证退出时 kill server、依次跑 pipeline=1 与 pipeline=32，并打印 uname/cpu/rustc。
